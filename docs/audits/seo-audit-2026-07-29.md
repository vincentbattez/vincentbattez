# Audit SEO — vincentbattez.dev (29/07/2026)

**Périmètre** : site complet (`/` + `/go/*`), technique + on-page + contenu.
**Hypothèses** : pas d'accès Search Console → aucune donnée d'indexation ni de
Core Web Vitals terrain ; les métriques perf citées sont **lab** (dernier run
Lighthouse CI local du 22/07/2026, `.lighthouseci/`).

---

## Résumé exécutif

Les fondations techniques sont **excellentes** : robots, sitemap, canonical,
JSON-LD, en-têtes de sécurité, PWA, `llms.txt`, pages `/go` proprement en
`noindex` + canonical. Lighthouse SEO = 100/100. Rien ne bloque l'indexation.

Le problème n'est pas technique, il est **stratégique** : les métadonnées
vendaient « des applications web robustes en Node/React/Vue/TS », c'est-à-dire
l'argumentaire indifférencié de n'importe quel freelance full-stack — alors que
le positionnement réel est *développeur full-stack senior qui code avec l'IA et
qui tient que l'architecture n'a jamais été aussi critique*. Et il n'existe
qu'**une seule URL indexable** de 502 mots.

**Top 3 priorités**
1. ~~Porter le différenciateur (architecture à l'ère de l'IA) dans les
   métadonnées et le JSON-LD~~ — ✅ fait le 29/07 (finding #1)
2. **Créer une surface de contenu** — le site ne peut ranker que sur son nom (P1, ouvert)
3. Brancher Search Console — angle mort de cet audit (P1, ouvert)

Les quick wins techniques (titre, `<h2>`, `htmlLang`, code mort) sont faits.

## Findings

### 1. Le différenciateur est absent des métadonnées — P1

> **Révisé le 29/07 après clarification du positionnement.** La version initiale
> de ce finding partait de `docs/product.md` (« freelance **AI Engineer** ») et
> concluait qu'il fallait ranker sur « développeur IA ». C'était **faux** :
> `product.md` était périmé. Le positionnement réel est *développeur full-stack
> senior qui code avec l'IA et qui insiste sur l'importance de l'architecture,
> surtout à l'ère de l'IA*. L'IA est la **manière de travailler**, pas le
> service vendu. `product.md` a été corrigé pour verrouiller ce point.

**Problème** — Le rôle (`Développeur Full-Stack Senior`) était correct dans les
métadonnées. Ce qui manquait, c'est le **différenciateur** : les descriptions
vendaient des « applications web robustes (Node.js, React, Vue.js,
TypeScript) » — l'exact argumentaire de n'importe quel freelance full-stack.

**Évidence (avant correction)**
- `<meta name="description">` : « …applications web robustes : Node.js, React, Vue.js, TypeScript. » — ni architecture, ni IA
- `seo.keywords` : aucune occurrence de IA / assisté par IA / dette technique
- JSON-LD `personKnowsAbout` en **contradiction** avec le rôle : *Artificial Intelligence, RAG, LLM, Context Engineering, Prompt Engineering* en tête de liste, `Software Architecture` **absent** — signal « AI Engineer » exactement inverse du positionnement
- Seule trace indexable de l'argument : le `<h2>` du hero et le corps des tooltips

**Impact** — Le site se battait sur « développeur full-stack freelance Lille »,
requête saturée, sans aucun angle. Et le JSON-LD envoyait aux moteurs un signal
métier faux.

**⚠️ Ce qu'il ne faut PAS faire** — Bourrer « IA » dans le title pour viser
« développeur IA freelance ». Ce n'est pas le métier vendu, et le volume de
recherche sur « développeur qui code avec l'IA » est quasi nul. La valeur de ce
positionnement est en **conversion** (le CTO qui a déjà pris une refonte dans
les dents comprend l'argument en 3 secondes) et en **citation par les moteurs
de réponse**, pas en volume SERP.

**Fix — ✅ appliqué**

| Élément | Après |
|---|---|
| `descriptionMeta` (133 car.) | « …Je code avec l'IA sans sacrifier l'architecture. Node.js, React, Vue.js, TypeScript. » |
| `descriptionCard` (138 car.) | « …Je code avec l'IA, j'architecture pour que ça tienne. Node.js… » |
| `keywords` | + `Développement assisté par IA`, `Dette technique` — cosmétique, la balise est ignorée par Google (cf. finding #8), mise à jour uniquement pour ne pas laisser une SSOT contradictoire dans `config/seo.ts` |
| `personKnowsAbout` | **réordonné** : `Software Architecture` → `Full Stack Development` → `AI-Assisted Development` → `Technical Debt` → contexte/prompt/LLM → stack. **RAG retiré** (capacité produit non vendue). |
| `occupationSkills` / `serviceKnowsAbout` | idem : architecture d'abord, IA comme méthode |
| `personDescription` / `serviceDescription` | portent l'argument « tenir à cette vitesse » |
| `docs/product.md` | section **Positioning** ajoutée, avec un « do not rebrand as AI Engineer » explicite |

La stack (Node.js, React, Vue.js, TypeScript) est **conservée partout** : c'est
ce sur quoi les CTO recherchent réellement. Le différenciateur s'ajoute, il ne
remplace pas.

**Non touché : `seo.role`** — Il est juste, donc la contrainte des 3 mots du
stagger (`pages/index-motion.scss`) ne se pose plus. Le hero `<h2>`
(« Développeur Full-Stack / Architecture & IA ») exprime déjà exactement le
positionnement.

**Note — `config/llms.ts` était déjà aligné** et reste la meilleure formulation
du positionnement dans le repo : « profil rare combinant une architecture
backend robuste (DDD, hexagonale) et une maîtrise avancée du développement
assisté par IA ». C'est la matière première des pages de service du finding #3.

### 2. Le hero n'est plus piloté par la SSOT — P2 (bloque le fix #1)

**Évidence** — `pages/index.vue:102-108` : le `v-for="(word, i) in heroWords"`
est commenté, remplacé par trois `<span>` codés en dur
(« Développeur / Full-Stack / Architecture & IA »). La variable `heroWords`
(`pages/index.vue:18`) est calculée mais **plus utilisée**.

**Impact** — Changer `seo.role` mettra à jour title, description, keywords,
JSON-LD… mais **pas** le titre visuel. Divergence garantie au prochain
repositionnement.

**Fix — ✅ appliqué** — Option « découplage assumé » retenue : `heroWords` et le
bloc `v-for` commenté supprimés, commentaire mis à jour pour dire explicitement
que le `<h1>` (kicker) suit la SSOT mais que le `<h2>` visuel est codé en dur.

**Conséquence pour le finding #1** — Changer `seo.role` mettra à jour title,
description, keywords, `<h1>` et JSON-LD, mais **pas** le `<h2>` visuel : à
éditer à la main dans `pages/index.vue`, en gardant 3 blocs `.vb-word` (stagger).

### 3. Surface de ranking : une seule URL, 502 mots — P1 (long terme)

**Évidence** — `sitemap.xml` ne contient que `https://vincentbattez.dev/`.
Texte visible extrait du HTML statique : **502 mots**, tooltips inclus.

**Point positif** — Le contenu des `VbTooltip` (architecture, dette technique,
compréhension profonde, refonte) **est bien présent dans le HTML statique**,
donc crawlable. Ce n'est pas du contenu masqué au crawler.

**Impact** — Une page unique ne peut ranker que sur le nom de marque et
éventuellement une requête locale. Aucune couverture de longue traîne, aucune
possibilité de maillage interne, aucun signal E-E-A-T (pas de preuve
d'expérience : ni études de cas, ni articles, ni réalisations).

**Fix (long terme, ordre de rentabilité)**
1. 2–3 **pages de service** : « Intégration IA / LLM », « Architecture
   logicielle », « Refonte & dette technique » — chacune reprend et développe
   un tooltip existant (le contenu est déjà écrit, il est juste compressé)
2. **Études de cas** : le signal E-E-A-T le plus fort pour du freelance
3. Un espace **notes/articles** si le rythme de publication est tenable —
   sinon s'abstenir plutôt que produire du thin content

### 4. Hiérarchie de titres : un `<h1>`, zéro `<h2>`/`<h3>` — P2

**Évidence** — Sur 580 lignes de `pages/index.vue`, un seul heading. Le
`<h1>` est le *kicker* (petit texte), tandis que l'élément visuellement
dominant (« Développeur Full-Stack Architecture & IA ») est un `<p>`, et les
termes des tooltips (`Architecture`, `Compréhension profonde`, `Dette
technique`, `Refonte`) — le cœur sémantique de la page — n'ont aucun poids
structurel.

**Impact** — Moyen. Google comprend une page courte sans hiérarchie, mais les
headings sont un signal fort de structure pour les extraits et pour les moteurs
de réponse (AI Overviews, Perplexity).

**Fix — ✅ appliqué (partiellement)** — La recommandation initiale (« passer les
termes-tooltips en `<h2>` ») était **mauvaise** : le `term` de `VbTooltip` vit
dans un `<span role="tooltip">` téléporté sous `<body>`, et le déclencheur est
un `<button>` inline dans un `<p>` — un heading y serait à la fois invalide et
hors flux. Retenu à la place : `pages/index.vue:101`, le titre visuellement
dominant est passé de `<p class="vb-hero--title">` à `<h2>` (styles portés par
les classes, preflight Tailwind actif → rendu identique). La page a désormais
1 × `<h1>` + 1 × `<h2>`, et « Architecture & IA » porte un poids sémantique.

**Reste** — Une vraie hiérarchie à 3 niveaux n'a de sens qu'avec les pages de
service du finding #3. Ne pas ajouter de `<h3>` artificiels ici.

### 5. LCP à 2,7 s (lab) — P2

**Évidence** — `.lighthouseci/` (22/07, localhost throttlé) : perf 0,93,
LCP **2,7 s** (> seuil 2,5 s), FCP 2,4 s, CLS 0,032 ✅, TBT 10 ms ✅.

Le LCP est le portrait (`/images/vincentbattez.webp`, 56 Ko), déjà préchargé
avec `fetchpriority="high"` (`pages/index.vue:33-38`). Le FCP à 2,4 s indique
que le blocage est **avant** l'image : CSS d'entrée en `<link>` bloquant
(`features.inlineStyles: false`) + chargement des polices.

**Impact** — Faible à moyen. CLS et INP sont bons ; seul le LCP est en zone
« à améliorer ». Pas de donnée terrain pour confirmer.

**Fix**
- Ouvrir Search Console → rapport Signaux Web essentiels pour trancher sur du
  terrain avant d'optimiser à l'aveugle
- Si confirmé : `preload` de la police Nunito 700 (celle du hero) et
  `font-display: optional` plutôt que `swap` sur les poids décoratifs
- Le trade-off `inlineStyles: false` est documenté et justifié — ne pas le
  revenir sans mesure

**Impact** — Nul en SEO, réel en UX (retour arrière plus lent). Cosmétique ici,

### 7. `lang="fr"` vs `htmlLang: "fr-FR"` — P3

**Évidence** — `config/seo.ts` définit `htmlLang: "fr-FR"`, le HTML servi
contient `<html lang="fr">` — `@nuxtjs/seo` impose `defaultLocale`.

**Impact** — Nul. Les deux valeurs sont valides, site monolingue, aucun
hreflang nécessaire. Seule l'ambiguïté du code posait problème.

**Fix — ✅ appliqué** — `seo.htmlLang` supprimé (il annonçait le contraire de ce
qui était servi) ; `nuxt.config.ts` utilise `seo.defaultLocale`. HTML servi
inchangé (`lang="fr"`), une seule source de vérité. `seo.language` (`fr-FR`)
reste pour `site.language` et `inLanguage` du JSON-LD.

---

### 8. `<meta name="keywords">` — P3

Ignorée par Google depuis 2009. Inoffensive, mais elle entretient l'illusion
que le ciblage mots-clés est fait. Le vrai ciblage passe par title / h1 /
contenu (cf. finding #1).

## Ce qui est correct (à ne pas toucher)

| Élément | État |
|---|---|
| `robots.txt` | ✅ `Allow: /` + référence sitemap |
| `sitemap.xml` | ✅ valide, `lastmod`, `/go/**` exclu, image incluse |
| Canonical | ✅ auto-référent sur `/`, `redirectToCanonicalSiteUrl: true` |
| JSON-LD | ✅ **présent dans le HTML statique** (Person, ProfessionalService, WebSite, WebPage, ImageObject, `@id` correctement chaînés) |
| Pages `/go/*` | ✅ `noindex, nofollow` + canonical vers `/` → aucun thin content indexé |
| HTTPS / sécurité | ✅ HSTS preload, CSP de base, `nosniff`, `frame-ancestors none` |
| OG / Twitter | ✅ image statique 1200×630 (HTTP 200), alt, dimensions |
| Cache | ✅ immutable sur assets fingerprintés |
| `llms.txt` | ✅ HTTP 200, charset explicite |
| Lighthouse SEO | ✅ 100/100, assertion CI bloquante à `minScore: 1` |
| Alt du portrait | ✅ descriptif et dérivé de la SSOT |
